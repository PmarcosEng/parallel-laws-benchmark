1. O Projeto

Este benchmark mede, de forma rigorosa e reproduzível, o desempenho de três algoritmos de busca executados em quatro modos: serial (1 thread), paralelo com OpenMP (CPU multi-core), GPU simulada (algoritmo de dois passos na CPU com 896 threads lógicos) e GPU real (kernel CUDA na GTX 1650). O objetivo central é observar, com dados reais, como as Leis de Amdahl e Gustafson se aplicam a cargas distintas.

Metodologia de medição

Cada configuração é executada 1 vez de warmup (descartada) seguida de 3 medições reais, usando a mediana como resultado final. Esse protocolo elimina dois tipos de ruído:

  • Cache fria — a primeira execução carrega dados na L3/L2; as seguintes encontram dados quentes. O warmup garante que medimos o estado estacionário.
  • Picos de agendamento — o sistema operacional pode interromper o processo por ~100 µs. A mediana de 3 descarta o pior caso sem esconder o comportamento típico.
/* Código em benchmark.c */
static double mediana3(double a, double b, double c) {
    if (a > b) { double t = a; a = b; b = t; }
    if (b > c) { double t = b; b = c; c = t; }
    if (a > b) { double t = a; a = b; b = t; }
    return b; // elemento central após ordenação dos 3
}

Por que 96 bytes por evento? A struct Event contém ID (4B), timestamp (8B), valor float (4B), categoria (4B) e padding para alinhar a 64 bytes — total 96 bytes. Esse tamanho faz cada linha de cache (64B) conter menos de um evento completo, aumentando as cache misses para acesso não-sequencial.

Por que o gargalo de memória domina

Para a busca linear com 10 M eventos:

  • Trabalho útil: comparar event.valor com [45.0, 55.0] — ~1 operação de FP por evento
  • Gargalo real: carregar 960 MB da RAM para os registradores — memória, não computação
  • Roofline: a CPU atinge ~50 GFLOPS mas está limitada a 50 GB/s de RAM → ~1 FLOP/byte → operação memory-bound
Intensidade Aritmética = FLOPs / Bytes = ~10M / 960M ≈ 0.01 FLOP/byte Muito abaixo do ridge point (~25 FLOP/byte do Ryzen 7 4800H) → completamente memory-bound

Cache lines e striding

O hardware busca memória em blocos de 64 bytes (cache line). Com eventos de 96 bytes, cada cache line contém menos de um evento completo — dois acessos consecutivos envolvem duas cache lines diferentes. Isso pressiona mais o controlador de memória do que dados menores que 64 bytes.

/* struct Event = 96 bytes → 1.5 cache lines por elemento */
typedef struct {
    uint32_t  id;           // 4 bytes
    double    timestamp;    // 8 bytes
    float     valor;        // 4 bytes
    uint32_t  categoria;    // 4 bytes
    // ... campos adicionais + padding até 96 bytes
} Event;
/* 10.000.000 × 96 bytes = 960 MB no heap */

3. Complexidade Big-O

Big-O descreve como o número de operações cresce com o tamanho da entrada. Mas para entender paralelismo, precisamos também saber se as operações são independentes (paralelizáveis) ou têm dependências (sequenciais).

Tabela comparativa — n = 10.000.000

AlgoritmoComplexidadeOperações em n=10MTempo serial típicoParalelizável?Motivo
Busca LinearO(n)~10.000.000 comparações~90–100 msSimCada elemento é independente — divide o array igualmente
Busca BináriaO(log n)~23 comparações~1–2 µsNãoCada passo depende do anterior — cadeia de dependência
Hash Lookup (×10K)O(1) por lookup~10.000 cálculos de hash~5–20 msSim10K lookups independentes — nenhuma dependência entre eles

O paradoxo: O(log n) mais lento de paralelizar

Contra-intuitivamente, o algoritmo mais eficiente assintoticamente é o pior candidato para paralelismo:

  • Busca binária serial: ~23 comparações, ~2 µs — rapidíssimo.
  • Overhead de criar 8 threads: ~1 ms — 500× mais lento que o trabalho.
  • Resultado: paralelizar busca binária com OpenMP gera speedup < 1.

Paralelizabilidade e granularidade

Para paralelismo valer a pena, o trabalho por thread precisa ser suficientemente grande para amortizar o overhead de sincronização (~10–100 µs). Regra prática:

  • Trabalho serial < 100 µs → não paralelize (overhead > ganho)
  • Trabalho serial 100 µs – 10 ms → avalie com cuidado (depende de fs)
  • Trabalho serial > 10 ms → bom candidato (overhead é < 1% do total)
log₂(10.000.000) = log₂(10⁷) ≈ 23.25 → 23 comparações Cada comparação ≈ 4 ns (L1 hit) → trabalho total ≈ 92 ns ≈ 0.1 µs

4. Lei de Amdahl

Gene Amdahl (1967) formulou um limite teórico para o speedup de programas parcialmente paralelizáveis: a fração serial do programa limita o speedup máximo, independentemente de quantos processadores você use.

Derivação

Seja T o tempo total serial. Divida-o em fração serial fs e paralela (1 − fs):

T(N) = T × fs + T × (1 − fs) / N N = número de workers; a parte paralela é dividida igualmente
S(N) = T / T(N) = 1 / ( fs + (1 − fs) / N ) Speedup de Amdahl — quanto menor fs, maior o potencial de ganho

No limite N → ∞, o speedup máximo absoluto é:

S(∞) = 1 / fs Com fs = 0.10 (10% serial), o teto é 10×, mesmo com milhões de threads

5% (0.05)1.90×3.48×5.93×8.83×20×
10% (0.10)1.82×3.08×4.71×6.40×10×
20% (0.20)1.67×2.50×3.33×3.81×5×

Como estimamos fs dos dados medidos

Invertendo a fórmula de Amdahl com N=8 threads e o speedup observado S:

fs = (N/S − 1) / (N − 1)   com N = 8 Exemplo: S = 1.78× com 8 threads → fs = (8/1.78 − 1)/(8 − 1) ≈ 0.50 → teto teórico = 2×

Esse fs estimado captura todo o overhead serial: junção de resultados, alocação de memória, sincronização de threads — não apenas o código explicitamente serial.

Limitação de Amdahl: a lei assume que o tamanho do problema é fixo. Na prática, quando você tem mais processadores, muitas vezes processa mais dados no mesmo tempo — e a Lei de Gustafson captura esse cenário de forma mais realista.

5. Lei de Gustafson

John Gustafson (1988) propôs uma visão diferente: em vez de perguntar "quanto mais rápido resolvo o mesmo problema?", pergunte "quanto mais trabalho consigo fazer no mesmo tempo?"

Formulação

Se fs é a fração serial medida no sistema paralelo (não no serial), então o speedup escalado de Gustafson é:

SG(N) = N − fs × (N − 1) O speedup cresce linearmente com N quando o volume de dados cresce proporcionalmente

Comparação Amdahl × Gustafson

Como aparece nos dados

No gráfico "Speedup com 8 threads × volume" do dashboard, você está vendo Gustafson na prática: se o speedup sobe conforme o volume aumenta, significa que a fração paralela do trabalho cresce mais rápido que o overhead serial — comportamento clássico de weak scaling.

Por que o speedup não continua subindo? A banda de memória DDR4 (~50 GB/s) é um recurso compartilhado. Com 8 threads lendo em paralelo, todas competem pela mesma largura de banda — o ganho satura quando o barramento está saturado, não quando a CPU fica ociosa.

Parâmetros

7. Busca Linear — O(n)

A busca linear percorre todos os eventos sequencialmente, comparando event.valor com o intervalo [45.0, 55.0]. É o algoritmo mais simples e, paradoxalmente, o que mais se beneficia de paralelismo com grandes volumes.

Implementação

/* search.c — busca_linear_serial() simplificado */
SearchResult busca_linear_serial(const Event *dados, int n,
                                    float min, float max) {
    int count = 0;
    for (int i = 0; i < n; i++) {           // O(n) — visita todos
        if (dados[i].valor >= min &&
            dados[i].valor <= max)
            count++;
    }
    // retorna SearchResult com count
}

/* Versão OpenMP */
#pragma omp parallel for reduction(+:count) schedule(static)
for (int i = 0; i < n; i++) {
    if (dados[i].valor >= min && dados[i].valor <= max)
        count++;
}

Cálculo do gargalo de memória

Para n = 10 M eventos:

  • Dados a ler: 10.000.000 × 96 bytes = 960 MB
  • Bandwidth DDR4 efetivo: ~50 GB/s (dual channel, benchmark Stream Triad)
  • Tempo teórico mínimo: 960 MB ÷ 50.000 MB/s = ~19 ms
  • Tempo real medido: ~92 ms (serial, 1 thread)
960 MB ÷ 50 GB/s = 0.0192 s ≈ 19 ms (teórico) Real: ~92 ms → eficiência de memória ~21% (cache misses, TLB, paginação, prefetcher)

Por que 1.8× e não 8× com 8 threads?

Este é o resultado mais importante do benchmark. A resposta envolve três fatores:

  1. Gargalo de bandwidth compartilhado: 8 threads lendo a RAM ao mesmo tempo competem pelo mesmo barramento DDR4 (~50 GB/s). O bandwidth total não se multiplica por 8 — ele é limitado pelo controlador de memória.
  2. Fração serial não-nula: junção dos resultados parciais (reduction(+:count)), overhead de criação e destruição do pool de threads (~1–2 ms), distribuição de trabalho.
  3. Hyperthreading (SMT): threads 9–16 compartilham recursos físicos com threads 1–8. Para workloads memory-bound, SMT ajuda pouco porque o gargalo é a memória, não a unidade de execução.

8. Busca Binária — O(log n)

A busca binária encontra um elemento em um array ordenado descartando metade do espaço de busca a cada comparação. Com 10 M elementos, são apenas 23 comparações — mas essas 23 comparações formam uma cadeia de dependências que impossibilita paralelismo.

Implementação e dependência de dados

SearchResult busca_binaria_serial(const Event *dados, int n, float alvo) {
    int lo = 0, hi = n - 1;
    while (lo <= hi) {
        int mid = lo + (hi - lo) / 2;    // mid depende de lo e hi anteriores
        if      (dados[mid].valor < alvo) lo = mid + 1;  // lo depende de mid
        else if (dados[mid].valor > alvo) hi = mid - 1;  // hi depende de mid
        else { /* encontrou */ break; }
    }
}

Cada iteração só pode começar quando a anterior terminar — a variável mid depende de lo e hi que dependem do resultado anterior. Essa cadeia de dependência é o oposto de uma operação paralelizável.

Por que overhead > trabalho

ComponenteTempo típicoObservação
23 comparações (L1 quente)~0.1–0.2 µs~4 ns × 23 passos dependentes
Criar pool de 8 threads (OpenMP)~1–5 msFirst call; pool reutilizado depois
Pool reutilizado (warmup feito)~50–200 µsAinda 250× maior que o trabalho
Barreira de sincronização~10–50 µsTodos os threads precisam terminar

Resultado: speedup da busca binária com OpenMP é tipicamente 0.01× a 0.1× — 10× a 100× mais lento que o serial. O trabalho útil é ~0.1 µs, o overhead é ~1000× maior.

A "paralelização" da GPU simulada

O modo gpu_sim na busca binária divide o array em 896 segmentos e faz busca binária em cada segmento. Isso é semanticamente diferente — em vez de buscar um único alvo com 23 comparações, faz 896 buscas de 23 comparações cada. O resultado (se encontrou) é o mesmo, mas o modelo computacional é diferente da busca binária clássica.

9. Hash Lookup — O(1)

O hash lookup usa uma função de hash para mapear um ID diretamente para um bucket na tabela, evitando a necessidade de comparar com todos os elementos. Com um bom hash e fator de carga controlado, o lookup é O(1) amortizado.

Função de hash: Knuth Multiplicative

h(k) = (k × 2654435761) >> (32 − log₂(M)) Constante 2654435761 ≈ φ × 2³² (proporção áurea) — distribui uniformemente para qualquer M potência de 2 
/* Knuth multiplicative hash — distribuição uniforme */
static inline uint32_t hash_fn(uint32_t key, uint32_t bits) {
    return (key * 2654435761u) >> (32 - bits);
}
/* bits = log2(n_buckets); garante índice no range [0, n_buckets) */

Separate Chaining

Colisões são resolvidas com separate chaining: cada bucket aponta para uma lista ligada de elementos com o mesmo hash. Com fator de carga controlado, a lista média tem ≤1 elemento.

typedef struct HashNode {
    uint32_t id;
    const Event *event;
    struct HashNode *next;   // encadeamento para colisões
} HashNode;

typedef struct {
    HashNode **buckets;      // array de cabeças de lista
    uint32_t   n_buckets;    // potência de 2
    uint32_t   bits;         // log2(n_buckets)
} HashTable;

Fator de carga

O fator de carga α = n_elementos / n_buckets determina o comprimento médio das listas. Neste benchmark, α ≈ 0.76 (76%):

Quando paralelismo ajuda no hash

O benchmark realiza 10.000 lookups independentes — cada lookup busca um ID diferente, sem dependência entre eles. Isso é embarrassingly parallel: ideal para OpenMP e GPU.

/* OpenMP sobre 10K lookups independentes */
#pragma omp parallel for schedule(static) num_threads(th)
for (int i = 0; i < n_ids; i++) {
    SearchResult r = hash_lookup_serial(ht, ids[i]);
    results[i] = r.count;
    search_result_free(&r);
}

Paralelo ajuda no hash quando há muitos lookups independentes (N_IDS_HASH = 10.000 neste benchmark). Se fosse apenas 1 lookup, o overhead dominaria como na busca binária.

10. Reduce Paralelo — O(n) ideal para GPU

O reduce paralelo é o algoritmo clássico do paralelismo em GPU. Conta quantos eventos têm valor no intervalo [45, 55] usando uma redução em árvore: cada thread calcula um resultado parcial, depois os resultados são combinados em log₂(N) passos — sem nenhuma dependência entre elementos.

Por que é o algoritmo ideal para GPU? Três razões combinadas: (1) nenhuma dependência entre elementos → fp ≈ 100%; (2) sem array de saída grande → sem writes espalhados na VRAM; (3) redução usa shared memory (on-chip, ~10× mais rápida que VRAM global) → quase zero latência de memória na fase de combinação.

Comparação com Busca Linear

Implementação — três variantes

Serial — baseline

/* search.c — reduce_paralelo_serial() */
SearchResult reduce_paralelo_serial(Event *dados, int n, float min, float max) {
    int count = 0;
    for (int i = 0; i < n; i++) {
        if (dados[i].valor >= min && dados[i].valor <= max)
            count++;
    }
    SearchResult r = {NULL, count}; // itens=NULL: só precisamos da contagem
    return r;
}

OpenMP — redução canônica (fp ≈ 100%)

A cláusula reduction(+:count) é a forma mais pura de paralelismo: cada thread mantém um acumulador local, e a runtime OpenMP soma tudo com uma árvore interna. Não há fase serial de junção — o overhead é mínimo.

/* search.c — reduce_paralelo_openmp() */
int count = 0;
#pragma omp parallel for reduction(+:count) schedule(static)
for (int i = 0; i < n; i++) {
    if (dados[i].valor >= min && dados[i].valor <= max)
        count++;
}
// Sem malloc, sem merge serial, sem temp arrays — fp mínimo

Contraste com busca_linear_openmp(): a versão linear usa arrays temporários por thread + fase serial de merge (ver search.c linhas 54–106). O reduce usa apenas reduction(+:count) — a runtime faz tudo. Resultado: fs próximo de 0, speedup deve ser quase linear com N threads.

GPU Simulada — estrutura de blocos

/* search.c — reduce_paralelo_gpu_sim() — espelha estrutura CUDA */
const int THREADS_POR_BLOCO = 256;
const int N_BLOCOS = (n + THREADS_POR_BLOCO - 1) / THREADS_POR_BLOCO;

/* fase 1: cada "bloco" conta sua fatia (paralela na GPU) */
for (int b = 0; b < N_BLOCOS; b++) {
    int ini = b * THREADS_POR_BLOCO;
    int fim = min(ini + THREADS_POR_BLOCO, n);
    for (int i = ini; i < fim; i++)
        if (dados[i].valor >= min && dados[i].valor <= max) contadores[b]++;
}
/* fase 2: soma parciais (log2 passos com shared memory na GPU real) */
for (int b = 0; b < N_BLOCOS; b++) total += contadores[b];

GPU Real (CUDA) — kernel com shared memory

/* search_cuda.cu — kernel_reduce_count() */
__global__ void kernel_reduce_count(
    const Event* __restrict__ dados, int n,
    float vmin, float vmax, int* __restrict__ d_result)
{
    extern __shared__ int sdata[];    // on-chip, ~10× mais rápida que VRAM
    int tid = threadIdx.x;
    int i   = blockIdx.x * blockDim.x + threadIdx.x;

    sdata[tid] = (i < n && dados[i].valor >= vmin && dados[i].valor <= vmax) ? 1 : 0;
    __syncthreads();

    // redução em árvore: log2(256) = 8 passos na shared memory
    for (int s = blockDim.x >> 1; s > 0; s >>= 1) {
        if (tid < s) sdata[tid] += sdata[tid + s];
        __syncthreads();
    }
    if (tid == 0) atomicAdd(d_result, sdata[0]); // 1 atomic por bloco
}

Análise de Amdahl

A redução paralela tem fs praticamente nulo porque:

  • Fase paralela: cada thread compara seu elemento independentemente — O(n/P)
  • Fase de redução: a runtime OpenMP faz uma árvore em O(log P) — negligível
  • Resultado: Amdahl prevê speedup próximo de N (linear scaling)
S(N) ≈ 1 / (0.001 + 0.999/N) ≈ N para N << 1000 fs ≈ 0.001 → teto teórico ≈ 1000× — na prática limitado pela bandwidth de RAM/VRAM

Por que GPU ainda pode ser mais lenta (H2D domina)

Mesmo com um kernel ideal, a GTX 1650 ainda precisa copiar os dados via PCIe:

Componente30M eventosObservação
H2D transfer (PCIe 3.0)~360 ms2,88 GB ÷ 8 GB/s — este é o gargalo
Kernel reduce (GPU)~5–15 msMuito rápido — shared memory + alta paralelização
D2H result (1 inteiro)~0 ms4 bytes — negligível
Serial CPU (baseline)~90–150 msRAM-bound mas sem overhead PCIe

Conclusão: o speedup do kernel CUDA puro (sem H2D) pode ser >10× sobre o serial. Mas o speedup com transferência (o que realmente importa quando os dados estão na CPU) continua negativo. Isso demonstra que a GPU só compensa quando os dados já estão na VRAM ou quando processamos múltiplas operações sem copiar de volta para a CPU a cada vez.

Lição central do artigo: o algoritmo ideal para GPU deve ter (1) alta intensidade aritmética, (2) dados que residem na VRAM entre operações, e (3) resultado pequeno. O reduce paralelo é o melhor candidato do projeto para isso.

11. Geração de Dados

Os eventos são gerados sinteticamente com distribuições estatísticas reais. A semente fixa 42 garante que os resultados são reproduzíveis entre execuções — você sempre gera o mesmo conjunto de dados.

Distribuição dos valores: Box-Muller

O campo valor (float) de cada evento segue uma distribuição normal com média μ = 50.0 e desvio padrão σ = 15.0. A transformação Box-Muller converte dois números uniformes em dois normais:

Z₀ = √(−2 ln U₁) × cos(2π U₂)    Z₁ = √(−2 ln U₁) × sin(2π U₂) U₁, U₂ ~ Uniform(0,1) independentes → Z₀, Z₁ ~ N(0,1) independentes 
/* generator.c — transformação Box-Muller */
static float randn(float mu, float sigma) {
    static float spare; static int has_spare = 0;
    if (has_spare) { has_spare = 0; return spare * sigma + mu; }
    float u = rand_uniform(), v = rand_uniform();
    float mag = sigma * sqrtf(-2.0f * logf(u));
    spare = mag * sinf(2.0f * (float)M_PI * v);
    has_spare = 1;
    return mag * cosf(2.0f * (float)M_PI * v) + mu;
}

Timestamps: distribuição de Poisson

Os timestamps simulam chegadas de eventos em um processo de Poisson (eventos chegam aleatoriamente a uma taxa constante λ). O intervalo entre chegadas segue distribuição exponencial:

Δt = −ln(U) / λ    U ~ Uniform(0,1) λ = 1000 eventos/segundo → interval médio = 1 ms

struct Event — 96 bytes

/* event.h */
typedef struct {             // offset  tamanho
    uint32_t  id;            //  0       4 bytes — identificador único
    uint32_t  categoria;     //  4       4 bytes — enum de categoria
    double    timestamp;     //  8       8 bytes — Unix timestamp (ns)
    float     valor;         // 16       4 bytes — valor medido ~N(50,15)
    float     valor2;        // 20       4 bytes — segundo valor
    uint8_t   flags;         // 24       1 byte  — bitmask de flags
    uint8_t   _pad[39];      // 25      39 bytes — padding até 64 bytes alinhado
    // segundo bloco de 32 bytes para completar 96
    uint64_t  extra[4];      // 64      32 bytes — dados extras
} Event;                      // total: 96 bytes = 1.5 cache lines
static_assert(sizeof(Event) == 96, "Event deve ter exatamente 96 bytes");

Por que semente 42?

A semente 42 é uma convenção ("the answer to everything") mas tem impacto real: qualquer execução em qualquer máquina com o mesmo gerador e semente 42 produz exatamente os mesmos dados. Isso é fundamental para comparar resultados entre máquinas — os dados são idênticos, só o hardware difere.

Importante: os dados gerados têm μ = 50.0 e σ = 15.0. A busca linear usa o intervalo [45.0, 55.0] = [μ−⅓σ, μ+⅓σ], que captura aproximadamente 26% dos eventos pela distribuição normal.

11. OpenMP

OpenMP é uma API de paralelismo de memória compartilhada para C/C++/Fortran. Diretivas de compilador (#pragma omp) marcam regiões paralelas que o runtime divide entre os threads disponíveis.

schedule(static) — por que escolhemos este

Para a busca linear, cada iteração tem custo idêntico (comparar um valor). schedule(static) divide o array em chunks iguais no início — sem overhead de scheduling dinâmico durante a execução.

scheduleDistribuiçãoOverheadMelhor para
staticChunks iguais, pré-calculadosMínimoCusto por iteração uniforme (nossa busca linear)
dynamicChunks atribuídos sob demandaMédioCusto variável por iteração (ex: árvores irregulares)
guidedChunks decrescentesMédioCarga desequilibrada com locality favorável

OMP_PROC_BIND e OMP_PLACES

/* benchmark.c — configurado antes do primeiro parallel */
_putenv("OMP_PROC_BIND=close");   // threads vizinhas → mesma LLC
_putenv("OMP_PLACES=cores");      // 1 thread por núcleo físico
  • OMP_PROC_BIND=close: threads são alocadas em processadores próximos entre si, maximizando o compartilhamento de L3 cache e reduzindo latência de acesso à memória de threads vizinhas.
  • OMP_PLACES=cores: cada thread ocupa um núcleo físico diferente, evitando que dois threads compartilhem os recursos de um mesmo núcleo SMT quando o trabalho é memory-bound.

False sharing

False sharing ocorre quando dois threads escrevem em variáveis diferentes que estão na mesma cache line (64 bytes). O hardware invalida a linha inteira para todos os outros cores, causando "cache bouncing" caro.

/* PROBLEMA: contadores adjacentes na mesma cache line */
int contadores[8];  // 8 × 4 bytes = 32 bytes → na mesma linha!
#pragma omp parallel for
for (int i=0; i<n; i++) contadores[omp_get_thread_num()]++;

/* SOLUÇÃO: reduction() — sem acesso compartilhado */
int count = 0;
#pragma omp parallel for reduction(+:count)
for (int i=0; i<n; i++)
    if (dados[i].valor >= min) count++;

SMT (Hyperthreading) e workloads memory-bound

O Ryzen 7 4800H tem 8 cores físicos / 16 threads lógicos (SMT 2-way). Para workloads compute-bound, SMT pode dar ~20–30% de throughput extra usando unidades de execução ociosas. Para workloads memory-bound como a busca linear, SMT frequentemente piora o desempenho:

  • 16 threads lógicos competem pela mesma bandwidth de DDR4 que 8 físicos
  • O L1/L2 de cada core é compartilhado entre os 2 threads SMT daquele core — mais evictions
  • O scheduler de hardware pode não favorecer os threads que têm os dados na cache

Para ver isso no dashboard: compare 8 threads vs 16 threads no volume 10 M. Se 16 threads tiver speedup ≤ 8 threads, o workload é memory-bound e SMT não ajuda.

12. GPU Simulada vs GPU Real

O que é a GPU Simulada

O modo gpu_sim é um algoritmo de dois passos executado na CPU, usando 896 threads lógicos (igual ao número de CUDA cores da GTX 1650). Não é CUDA. Não usa a GPU. É uma aproximação conceitual do paralelismo massivo.

O que é a GPU Real

O modo cuda executa um kernel real na GTX 1650 via CUDA. O timing inclui transferência H2D (Host → Device) via PCIe + execução do kernel + transferência D2H (Device → Host). O dashboard reporta separadamente o tempo do kernel puro e o tempo total H2D+kernel.

Por que o speedup CUDA pode ser <1×? Para o dataset de 960 MB, a cópia PCIe leva ~120 ms (960 MB ÷ 8 GB/s), que é mais lento que a busca serial (~92 ms). O kernel em si é muito rápido, mas o gargalo é o barramento PCIe 3.0 x8. Em aplicações reais, os dados já estariam na VRAM e esse custo seria zero.

13. Validade da Simulação

Este é o capítulo mais importante para interpretar os resultados corretamente. Nem tudo que este benchmark mede é cientificamente válido para todos os propósitos.

O que é cientificamente válido

  • Leis de Amdahl e Gustafson: os speedups medidos com OpenMP e CUDA demonstram genuinamente os princípios de ambas as leis. Os limites teóricos predizem bem os resultados.
  • Comparação serial vs OpenMP: totalmente válida. Mesmo hardware, mesma memória, apenas mais threads. O speedup reflete a paralelizabilidade real do algoritmo.
  • Gargalo de memória DDR4: válido e mensurável. A relação entre tamanho do dataset e speedup confirma o modelo memory-bound para busca linear.
  • Overhead de paralelismo: válido. O fs estimado por inversão de Amdahl é uma métrica real e útil do overhead de sincronização.
  • Timing com mediana de 3: metodologia sólida para eliminar ruído sem viesar para o melhor caso.
  • GPU Real (CUDA): mede corretamente o desempenho da GTX 1650 para este workload específico, incluindo o custo real de H2D+kernel+D2H.

O que NÃO é válido (limitações explícitas)

  • GPU Simulada ≠ GPU Real: o modo gpu_sim com 896 threads OpenMP não representa o desempenho real de uma GPU. GPUs têm arquitetura SIMD, warps, memória coalescente, e scheduler de hardware — nada disso é capturado por threads da CPU. Use gpu_sim apenas para entender o modelo de programação, não para prever performance.
  • Ambiente controlado vs produção: o benchmark roda isolado, sem carga de sistema, sem I/O concorrente, sem memória fragmentada. Em produção, fs real será maior.
  • Frequência de clock variável: o Ryzen 7 4800H usa boost que pode subir de 2.9 GHz (base) a 4.2 GHz (boost). Se o boost estiver ativo nos primeiros segundos e então thermal throttling ocorrer, os tempos seriais e paralelos podem ter sido medidos em frequências diferentes.
  • Um único algoritmo de busca: este benchmark mede três algoritmos específicos. Outros algoritmos (sorting, FFT, graph traversal) terão comportamentos completamente diferentes perante Amdahl e Gustafson.
  • Dados sintéticos vs dados reais: dados gerados com Box-Muller têm propriedades específicas (distribuição normal, sem clustering, sem correlação). Dados reais frequentemente têm padrões que afetam o desempenho de cache de forma diferente.
  • Portabilidade das conclusões: speedups medidos no Ryzen 7 4800H + DDR4 não se transferem diretamente para ARM, Intel com HBM, ou servidores com NUMA. Veja a seção 14 para como adaptar.

Anti-padrão comum: ver que a GPU Real tem speedup < 1× e concluir que "GPU é mais lento que CPU para busca". A conclusão correta é: "transferir 960 MB via PCIe é mais lento do que buscar na RAM, mas o kernel em si é muito mais rápido — olhe o speedup do kernel-only no terminal".

Checklist para citar estes resultados

  • [ ] Especifique o hardware exato (modelo CPU/GPU, velocidade RAM, geração)
  • [ ] Mencione que o benchmark usa dados sintéticos com semente 42
  • [ ] Separe "gpu_sim (CPU com 896 threads)" de "cuda (GTX 1650 real)"
  • [ ] Para CUDA, reporte tanto "kernel puro" quanto "H2D+kernel" separadamente
  • [ ] Reporte os valores absolutos (ms), não apenas speedups relativos
  • [ ] Mencione a versão do compilador e flags de otimização usadas

16. Glossário

Speedup S(N)
Razão entre o tempo serial e o tempo paralelo: S = T_serial / T_paralelo. Speedup 2× significa metade do tempo com N workers.
Eficiência E(N)
Fração do speedup ideal aproveitada: E = S(N) / N. E = 1.0 = perfeito; E = 0.5 com 8 threads = metade dos threads úteis.
Fração serial fs
Fração do tempo total que não pode ser paralelizada. Inclui código serial explícito + overhead de sincronização + junção de resultados.
Lei de Amdahl
S(N) = 1 / (fs + (1-fs)/N). Define o speedup máximo para problema de tamanho fixo. Pessimista mas realista para problemas não escalonáveis.
Lei de Gustafson
S(N) = N − fs×(N-1). Define o speedup quando o volume cresce com N. Mais otimista para aplicações de throughput.
Strong scaling
Medir como o tempo diminui com mais threads para o mesmo problema — perspectiva de Amdahl. "Quanto mais rápido resolvo isso?"
Weak scaling
Medir como o tempo permanece constante quando problema e threads crescem juntos — perspectiva de Gustafson. "Quanto mais trabalho faço no mesmo tempo?"
Memory-bound
Workload onde o gargalo é a largura de banda de memória, não a velocidade de computação da CPU. A busca linear em 10M eventos é memory-bound.
Compute-bound
Workload onde o gargalo é a velocidade de cálculo da CPU/GPU (FLOPS), e a memória é suficientemente rápida. Multiplicação de matrizes densas é compute-bound.
Cache line
Unidade mínima de transferência entre cache e RAM: 64 bytes em x86 moderno. Qualquer leitura busca 64 bytes mesmo se você precisar de apenas 1 byte.
False sharing
Quando dois threads escrevem em variáveis diferentes que estão na mesma cache line, causando invalidações desnecessárias entre cores. Resolvido com padding ou reduction.
SMT / Hyperthreading
Simultaneous Multithreading: cada core físico expõe dois (ou mais) threads lógicos ao OS. Ajuda em workloads compute-bound, pouco ou nada em memory-bound.
Warp (CUDA)
Grupo de 32 threads CUDA que executam a mesma instrução em lockstep (SIMT). A unidade fundamental de scheduling na GPU — se um thread diverge, os outros 31 esperam.
SM (Streaming Multiprocessor)
Unidade de processamento da GPU que contém vários warps e memória compartilhada. A GTX 1650 tem 14 SMs com 64 CUDA cores cada = 896 CUDA cores totais.
Coalescência (CUDA)
Padrão de acesso à memória onde threads de um warp acessam endereços consecutivos, permitindo que o hardware combine múltiplos acessos em uma transação. Fundamental para alto desempenho na GDDR5.
H2D / D2H
Host-to-Device / Device-to-Host: transferências de dados entre RAM do CPU (host) e VRAM da GPU (device) via barramento PCIe. Custo dominante em operações com pouca computação por byte.
PCIe bandwidth
Largura de banda do barramento PCIe entre CPU e GPU. PCIe 3.0 x16 = ~16 GB/s teórico, ~12 GB/s prático. PCIe 3.0 x8 (GTX 1650 em alguns slots) = ~8 GB/s prático.
Intensidade aritmética
FLOPs / bytes lidos. Determina se um workload é memory-bound (baixa intensidade) ou compute-bound (alta intensidade). Busca linear ≈ 0.01 FLOP/byte → extremamente memory-bound.
Roofline model
Modelo visual que plota intensidade aritmética vs throughput para determinar o gargalo atual. O "ridge point" é onde compute-bound e memory-bound se encontram.
Warmup
Execução descartada antes das medições reais, para "esquentar" cache, compilar JIT, inicializar pools de threads. Garante que medimos o estado estacionário.
Mediana vs Média
A mediana de 3 medições é mais robusta a outliers (picos de latência do OS) do que a média. A média seria dominada por um pico raro de 10× o normal.
Kernel (CUDA)
Função que executa na GPU, lançada pela CPU com a sintaxe kernel<<<grid, block>>>(args). Cada thread tem threadIdx e blockIdx únicos.
Fator de carga (hash)
α = n_elementos / n_buckets. Determina o comprimento médio das listas em separate chaining. α < 0.8 é considerado seguro para O(1) amortizado.
Embarrassingly parallel
Problema onde as tarefas são completamente independentes e não precisam de comunicação. Exemplos: 10K hash lookups independentes, renderização de pixels. Speedup teórico = N (linear).

Interpretando o breakdown GPU Real

O terminal mostra duas linhas para a GPU Real:

[GPU real] kernel puro: 1.234 ms (74.58x)  | H2D+kernel (speedup acima): 125.678 ms
  • Kernel puro (1.234 ms, 74×): o kernel CUDA sozinho, sem transferência. Este número mostra o poder real de computação da GTX 1650 para este workload. 74× significa que o kernel é 74 vezes mais rápido que o serial — mas esse número é otimista porque ignora o custo de mover os dados.
  • H2D+kernel (125.678 ms): o que o usuário realmente espera — inclui copiar 960 MB via PCIe (~120 ms) + kernel (~1.2 ms) + copiar resultado de volta. O speedup reportado no dashboard usa esse número, porque é o que seria medido em uma aplicação real.

Quando o kernel puro faz sentido: se os dados já estivessem na VRAM (processamento contínuo de stream de dados), o custo H2D seria zero e o speedup real seria ~74×. Em aplicações de deep learning, os pesos ficam permanentemente na VRAM — o PCIe não é um gargalo recorrente.

Verificando a integridade dos resultados

O campo resultados (coluna "Resultados" no terminal) deve ser idêntico para todos os modos de um mesmo algoritmo e volume. Se serial, openmp, gpu_sim e cuda retornam counts diferentes, há um bug na implementação paralela.

Interpretando a tabela de cores no dashboard

  • ■ Verde: speedup ≥ 2× — paralelismo compensa claramente
  • ■ Amarelo: 1× ≤ speedup < 2× — ganho marginal; avalie custo de complexidade
  • ■ Vermelho: speedup < 1× — paralelo mais lento; overhead domina

Sinais de ambiente instável

  • Tempo serial variando >10% entre execuções → thermal throttling ou background load
  • Speedup com 16 threads < speedup com 8 threads → SMT prejudicando, workload memory-bound
  • GPU Real mais lenta que GPU Sim → PCIe gargalo; dataset enorme; normal para 960 MB
  • Hash com speedup < 1× com >2 threads → false sharing ou lock contention

19. Aba "Busca de Eventos" — Como Ler os Gráficos

Esta aba aparece após carregar um JSON de busca. Ela contém 4 seções numeradas.

Seção 2 — Tempo serial × volume (escala log)

Gráfico de linhas com eixo Y logarítmico. Cada linha é um algoritmo. O eixo X é o volume de dados; o eixo Y é o tempo serial em segundos.

Como ler: um degrau vertical no eixo Y = 10× mais lento.
• ■ Busca Linear sobe quase linearmente com o volume — confirmando O(n).
• ■ Busca Binária permanece quase horizontal — apenas 23 comparações em qualquer volume.
• ■ Hash Lookup também quase horizontal — O(1) amortizado por lookup.
Se a linear sobe de 0.001s para 0.1s quando o volume vai de 1K para 100K (100×), isso confirma O(n).

São 4 gráficos (um por algoritmo). O eixo X mostra os modos: Serial, 2t, 4t, 8t, ... GPU Real. O eixo Y é o speedup. Cada linha colorida representa um volume de dados diferente.

Como ler as linhas:
• Linha cinza tracejada = teto teórico de Amdahl (estimado pela inversão da fórmula com o melhor speedup OpenMP). Monstra o limite teórico dado o overhead serial estimado.
• Linha vermelha tracejada = break-even (speedup = 1×). Abaixo dela = paralelo mais lento que serial.
• Linhas coloridas = um volume por cor. A linha mais alta geralmente corresponde ao volume maior (mais dados → mais trabalho por thread → melhor speedup).

Seção 4 — Lei de Gustafson: speedup × volume

Eixo X = volume de dados; Eixo Y = speedup com o máximo de threads disponível. Cada linha é um algoritmo.

Como ler: se uma linha sobe conforme o volume aumenta, o algoritmo escala bem à la Gustafson — o trabalho paralelo cresce mais rápido que o overhead serial. Se a linha cai com volume maior, o overhead de sincronização está dominando (típico da busca binária).

Comportamentos típicos que você verá:

  • Busca Linear: sobe de ~0.3× (1K ev) até ~1.8× (10M ev) — confirma Gustafson fraco: quanto mais dados, mais o paralelismo compensa.
  • Busca Binária: permanece bem abaixo de 1× em todos os volumes — não existe weak scaling porque o problema é inerentemente sequencial.
  • Hash: começa alto (~4×) e pode subir ou estabilizar — 10K lookups já são suficientes para amortizar o overhead.
  • Reduce: deve subir mais steeply que a Linear — fraction paralela próxima de 100%.

Carregue um JSON de runs/matematica_*/. Esta aba analisa Monte Carlo π e Mandelbrot 2D — algoritmos compute-bound com fração paralela próxima de 100%.

Seções 2 e 3 — Tempo serial e speedup

Os gráficos têm a mesma estrutura da aba Busca. A diferença esperada: o speedup é muito maior aqui porque fp ≈ 100%. Com 8 threads e fp = 0.001, a Lei de Amdahl prevê speedup ≈ 7.9× (quase linear).

O que procurar: o speedup de Monte Carlo com 8 threads deve ser próximo de 8×. Se for muito menor (ex.: < 5×), verifique se há false sharing nos geradores de número aleatório — cada thread deve ter seu próprio estado LCG.

Seção 5 — GPU vs CPU (cards de speedup)

Mostra o speedup da GPU Real em relação ao serial CPU para o maior volume. Para algoritmos compute-bound com fp ≈ 100%, a GPU pode mostrar speedups de 10× a 50× — muito melhor que na busca linear, porque:

  • Os dados de entrada são pequenos ou gerados on-the-fly (pouco H2D)
  • O kernel processa muitas operações de FP por byte lido (alta intensidade aritmética)
  • O resultado é apenas 1 número (D2H negligível)

Se o speedup GPU Real estiver próximo de 1× ou negativo para matemática densa, verifique se o build foi compilado com -DHAS_CUDA. O campo "build" no JSON deve ser "cuda", não "cpu".
